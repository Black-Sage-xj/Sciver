# 本地开发与 GitHub 发布

本地 `main` 是已核验代码的唯一主线。GitHub 的 `origin/main` 是上一次推送的主线；推送后，两者应指向同一个提交。日常运行的 Web 服务使用同一提交的干净部署工作树，部署记录应包含实际目录和提交号。部署工作树不用于开发，从而避免未提交修改被运行中的服务加载。

## 开发

1. 开始前检查 `git branch --show-current`、`git status --short`、暂存区和服务实际运行目录。detached HEAD、历史快照和未提交文件都不能仅凭目录名称当成最新 `main`。
2. 普通修复和已经接受的功能在本地 `main` 汇合。需要隔离时，从当前 `main` 创建短期工作树；完成后检查差异、运行相关验证、提交，再以 fast-forward 或经审阅的 cherry-pick 汇入 `main`。
3. 不把另一工作树的整个目录覆盖到 `main`。核对其原提交、未提交差异和当前实现，区分已经纳入的修改、需要迁移的功能和被新版修复替代的旧改法。
4. 未完成的修改保留在明确命名的本地功能分支。Graph Research 的实验性整合留在本地 `codex/graph-research`；暂不向 GitHub 推送。

报告生成、报告阅读和账号管理是 Sciver 主线功能。报告实现位于 `theory_master/report_synthesis/`，不需要安装 Graph Research。拆分可选依赖时，应逐项核对现有功能，而不是连同调用入口一起删除。

## 推送和部署

1. 推送前核对本地开发差异，明确本次纳入的提交和仍未提交的工作；查看精确的暂存内容。
2. 运行相关测试、前端构建和公开内容检查：

   ```sh
   python scripts/public_release_guard.py --ref HEAD --base origin/main
   ```

   账号凭据、Provider 配置、研究任务、私有测试集、运行日志和恢复快照保存在仓库外。公开题例只包含原始 Test0。隐私检查针对文件、历史和构建产物，不以删除正常功能代替。
3. 仅在获得推送授权后执行 `git push origin main`。避免 `git push --all` 和 `git push --mirror`。
4. 查看**本次提交**的 GitHub Actions，确认核心测试、Web 回归、独立安装和公开边界检查通过。报告检查还要在未安装 Graph Research 的环境中运行。
5. 服务部署使用同一提交的干净工作树，核对启动目录及配置，再检查已完成任务的报告入口、账号管理和任务列表。日常 `main` 若有并行开发中的修改，保留其原暂存状态；服务仍使用已核验提交的部署快照。重启服务本身不能证明部署了正确版本。

GitHub 上常驻一个 `main` 即可。用户下载当前源码时选择 `main`；软件包版本通过带版本号的 tag 和 Releases 提供。功能分支服务于开发协作，不是供用户选择的多个正式版本。

## 这次混乱的原因

- 原开发目录停在 detached HEAD，并积累了未提交修改；服务从另一份 `main` 工作树启动。提交号、文件内容和运行目录没有一起核对。
- 一部分修复已经通过汇总或 cherry-pick 进入主线，所以仅查看“哪些提交不在 main”会误把等效修改当成遗漏。
- 直接从正在开发的工作树运行服务，会在后续加载模块时读到其他任务刚写入的未提交代码。主线与服务的同提交关系必须通过干净部署快照维持。
- 隔离 Graph Research 依赖时，错误删除了主线需要保留的报告接口、按钮和作业实现。
- 测试通过只证明被测版本满足已有断言；它不能证明该版本包含原开发目录的全部既有功能。

后续发布以本地 `main` 的审阅提交为基础，保留私有的差异清单和部署记录，验证同一提交的代码、产物与运行页面。
