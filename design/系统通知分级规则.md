# TheoryMaster 事件、异常与通知的职责边界（2026-10-18）

三个层级共享事实来源，但**不共享展示语义**：

1. **重要事件 / Milestone**：只展示 `severity=important` 的真实科研或运行里程碑（例如 Preferred Focus 开始/结束）；不展示重试、JSON 修复、系统错误或通知回执。它回答“研究/任务发生了哪项有意义的转折”，不代表人工待办。
2. **异常记录 / Incident archive**：按 Cycle 和 `incident_id` 聚合 `error` / `attention` / `minor` 等生命周期。一个事故显示一个案例，显示最近记录和条数，展开可检查所有原始 `registered`、`recurred`、`resume_attempt`、`notification_sent` 等；不因发生恢复尝试而虚构已解决状态。没有 `incident_id` 的旧记录按 Cycle / kind / code / summary 归组。`important_events.jsonl`、`cycle_anomalies.jsonl` 继续**只追加**；此层是审计记录，不生成铃铛红点。
3. **通知 / Actionable inbox**：顶部铃铛只列出任务**当前**处于 `NEEDS_ATTENTION` / `FAILED` / `FAILED_RECOVERY` 的阻断。一项任务最多一个当前通知；重新运行到非阻断态后立即退出铃铛。红点统计当前未查阅且未清除的通知。打开铃铛列表会把已展示的通知标为已查阅；每条通知的“清除”按钮只从该浏览器的铃铛列表移除它。旧 Supervisor 会话仍从原处理历史查看，但不是当前通知。没有 Supervisor 会话也不能漏报真实停机。

**邮件**继续作为最后手段：仅在自动恢复与 Supervisor 决策后仍需人工介入的最终阻断，沿现有 SDK 去重规则发送；Collector 登记 transient `run.failed` 不直接 SMTP。**没有改变邮件发送策略或实际发送邮件。**

**去重与风险**：同一 `incident_id` 的多条生命周期只在 UI 合并，保留每条原始记录；不可通过 `resume_attempt`、`recurred`、通知回执推断已恢复。通知键包含任务、Cycle 和本次停机的 `registered` / `recurred` 发生记录；新的真实 stop 产生新键，旧已查阅或清除状态不会压住新通知。浏览器本地的已查阅和清除状态只控制铃铛，不写异常审计记录、科研结果，也不改变任务执行、恢复和科学裁决。其他浏览器有各自的通知状态。
